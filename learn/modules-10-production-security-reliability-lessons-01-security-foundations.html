Lesson 01 — Security foundations: threat modelling and the OWASP Top 10

Time: ~4 hours · Core

Why this matters

By now AdmitFlow holds thousands of students' contact details, sends messages in the institute's name, talks to a CRM, an AI provider and Google, and has a public endpoint. Each of those is a way in. Security isn't a feature added at the end; it's a habit of asking "how could this be abused?" about everything you build, and fixing the answers in priority order.

Threat modelling in 30 minutes

For each component in the architecture diagram, ask four questions (adapted from the threat-modelling community):

  1. What are we building? (the diagram, with data flows and trust boundaries)
  2. What can go wrong?
  3. What are we doing about it?
  4. Did we do a good job? (tests, reviews)

A simple prompt list for question 2, STRIDE:

ThreatQuestionAdmitFlow exampleControl
SpoofingCan someone pretend to be someone else?Forged webhook; stolen session tokenHMAC signatures; short-lived tokens; Google SSO
TamperingCan data be changed in transit or at rest?Edited form bodySignatures; HTTPS; database permissions
RepudiationCan someone deny doing something?"I never approved that message"Audit log (draft.approve, actor, time)
Information disclosureCan data leak?Counsellor sees another's leads; logs contain phone numbersRow-level checks; log redaction; RAG only public docs
Denial of serviceCan it be overwhelmed?Bot floods the public assistantRate limits; input caps; budgets
Elevation of privilegeCan someone gain powers they shouldn't have?Counsellor assigns leads; MCP agent sends messagesServer-side role checks; no send tool

Write the result as a table in the security review (Module 09 template), prioritized by likelihood × impact.

OWASP Top 10 (web applications), applied

The OWASP Top 10 lists the most common serious web risks. AdmitFlow's status:

RiskWhat it isAdmitFlow
Broken access controlUsers acting outside their permissionsRole and assignment checks on every route; tests for 401/403
Cryptographic failuresWeak or missing encryptionHTTPS; PBKDF2 password hashing; secrets in a secret manager
Injection (SQL, command, …)Untrusted input interpreted as codeSQLAlchemy parameters; no shell calls with user input
Insecure designMissing controls by designThreat model; approval gates by design (no send tool)
Security misconfigurationDefaults, open CORS, verbose errorsCORS allow-list; no stack traces to clients; security headers
Vulnerable componentsOutdated dependenciesPinned versions; dependency scanning (Lesson 04)
Identification & authentication failuresWeak login handlingRate-limited login; generic error messages; SSO
Software & data integrity failuresUnverified updates or dataSigned webhooks; CI-built images
Logging & monitoring failuresAttacks go unnoticedAudit log; metrics and alerts (Lesson 05)
Server-side request forgeryServer tricked into calling internal URLsAdmitFlow never fetches user-supplied URLs; keep it that way

For LLM features, use the OWASP Top 10 for LLM Applications as well (Module 08, Lesson 07).

If one layer fails (a bug in a role check), the others still limit the damage.

Secure by default

  • Deny by default: new routes require login (Module 04's break & fix)
  • Fail closed: missing webhook secret → 503, never "accept unsigned"
  • Least privilege: every user, service account, database role and AI tool gets only what it needs
  • Secure defaults in config: short session lifetime, strict CORS, production debug off

Check yourself

Draw AdmitFlow's current architecture with trust boundaries (internet ↔ API, API ↔ database, API ↔ third parties). Run STRIDE over the three most exposed components, and list your top five risks with the control for each (existing or needed).
