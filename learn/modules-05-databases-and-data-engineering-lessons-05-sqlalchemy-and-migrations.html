Lesson 05 — Python and databases: SQLAlchemy and migrations

Time: ~5 hours · Core

Why this matters

You'll rarely write raw SQL strings throughout an application. You'll use a library that manages connections, parameters and transactions, and maps rows to Python objects. And you'll need to change the schema safely on a database that already holds the client's data.

python -m pip install "sqlalchemy>=2.0" "alembic>=1.13" "psycopg[binary]>=3.2"

Connecting

from sqlalchemy import create_engine

engine = create_engine("sqlite:///admitflow.db")                                   # local file
engine = create_engine("postgresql+psycopg://admitflow:secret@localhost/admitflow") # PostgreSQL

The URL comes from the DATABASE_URL environment variable, never hard-coded (it contains a password).

Declaring tables as classes (ORM)

from typing import Optional
from datetime import datetime
from sqlalchemy import ForeignKey, String
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship

class Base(DeclarativeBase):
    pass

class LeadRow(Base):
    __tablename__ = "leads"
    lead_id: Mapped[str] = mapped_column(String(40), primary_key=True)
    received_at: Mapped[datetime] = mapped_column(index=True)
    email: Mapped[Optional[str]] = mapped_column(String(254), index=True)
    sources: Mapped[list["LeadSourceRow"]] = relationship(back_populates="lead", cascade="all, delete-orphan")

class LeadSourceRow(Base):
    __tablename__ = "lead_sources"
    lead_id: Mapped[str] = mapped_column(ForeignKey("leads.lead_id"), primary_key=True)
    source: Mapped[str] = mapped_column(String(20), primary_key=True)
    lead: Mapped[LeadRow] = relationship(back_populates="sources")

Optional[...] makes the column nullable; otherwise it's NOT NULL.

Querying with sessions

from sqlalchemy import select, func
from sqlalchemy.orm import Session, selectinload

with Session(engine) as s:
    query = (
        select(LeadRow)
        .where(LeadRow.sources.any(LeadSourceRow.source == "whatsapp"))
        .options(selectinload(LeadRow.sources))      # load channels in one extra query, not one per lead
        .order_by(LeadRow.received_at.desc())
        .limit(25)
    )
    leads = s.scalars(query).all()
    total = s.scalar(select(func.count()).select_from(LeadRow))

The N+1 problem

Without selectinload, accessing lead.sources for 25 leads runs 25 extra queries (1 + N). It's invisible in development and slow in production. Turn on echo=True on the engine to see every query SQLAlchemy runs, and count them.

Writing in a transaction

with Session(engine) as s, s.begin():
    s.add(LeadRow(lead_id="PHONE-1a2b3c4d", ...))
# committed here; rolled back if anything raised

The repository, again

SqlRepository (db.py) implements the same interface as JsonRepository. The API switches with one environment variable:

export DATABASE_URL=sqlite:///admitflow.db      # or postgresql+psycopg://...
admitflow serve

Contract tests (tests/test_repository_contract.py) run identical tests against both implementations. They caught a real difference while this module was written: the JSON store returned notes in the order saved, the SQL store in time order. The API tests also run against both stores.

Migrations with Alembic

You can't drop and recreate a production database to change its schema. Migrations are versioned scripts that move the schema forward (and back), applied in order.

export DATABASE_URL=sqlite:///admitflow.db
alembic upgrade head          # apply all migrations
alembic revision --autogenerate -m "add visits table"   # generate a migration from model changes
alembic check                 # fail if models and migrations have drifted
alembic downgrade -1          # undo the last migration

AdmitFlow's first migration: migrations/versions/0001_initial_schema.py. A test runs upgrade → check → downgrade → upgrade on every test run.

Migration rules for client databases:

  1. Always review autogenerated migrations. They can miss renames (seeing a drop + add, which loses data).
  2. Back up first and test the migration on a copy of production data.
  3. Make changes backward compatible where possible: add a nullable column, deploy code that writes it, backfill, then make it NOT NULL. Avoid renaming or dropping in one step while old code still runs.
  4. Commit migrations to Git with the code that needs them.

PostgreSQL locally

When you have Docker (Module 06):

docker run --name admitflow-db -e POSTGRES_USER=admitflow -e POSTGRES_PASSWORD=devpassword -e POSTGRES_DB=admitflow -p 5432:5432 -d postgres:16
export DATABASE_URL=postgresql+psycopg://admitflow:devpassword@localhost:5432/admitflow
alembic upgrade head

The project's CI workflow (Module 06) runs the whole test suite against a real PostgreSQL service on every pull request.
