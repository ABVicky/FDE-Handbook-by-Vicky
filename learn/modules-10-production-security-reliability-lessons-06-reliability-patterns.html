Lesson 06 — Reliability patterns

Time: ~3 hours · Core

Everything fails eventually

Databases restart, providers have outages, networks drop packets, tokens expire. Reliable systems assume failure and decide in advance what happens.

The patterns

PatternWhatAdmitFlow
TimeoutsNever wait foreverHTTP clients: 10–20 s; LLM calls bounded
Retries with backoffRetry transient failures, with growing waits and a capCRM reads/updates; httpx calls
Don't retry the permanent400/401/403 won't fix themselvesLesson from the incident: stop on 401 and alert
IdempotencySafe to repeatWebhooks, CRM sync, imports, outbox
Graceful degradationKeep the core working when a part failsNo model → offline assistant; no scorer → 503 on scoring only
Circuit breakerAfter repeated failures, stop calling a dependency for a whileStretch: around the LLM provider
BulkheadsIsolate parts so one can't exhaust shared resourcesOutbox runs as a separate job, not inside API requests
Health checksLiveness vs readiness (Module 06)/health, /ready
Queues / outboxAbsorb bursts and outagesApproved drafts wait in the outbox

Graceful degradation, concretely

Decide for each dependency: what do users see when it's down?

Dependency downUser experience
DatabaseAPI not ready (503); dashboard shows "AdmitFlow is temporarily unavailable"
LLM providerAssistant falls back to the offline engine; drafts use the template
Lead-scoring modelPriority list unavailable; everything else works
WhatsApp providerDrafts stay approved; outbox alert fires; email unaffected
CRMSync fails and reports; nothing else affected
Google sign-inAdmin break-glass password login

Load testing

Find limits before users do. Simulate realistic traffic (e.g. with Locust or k6) against staging, with production-like data volume (Module 05's big database):

  • 6 counsellors clicking through leads, plus a burst of 200 assistant questions per minute after an ad goes out
  • watch p95 latency, error rate, database CPU and connections

Then you can tell the client: "the current setup handles about N requests per second; beyond that, add instances or a larger database tier."

Capacity and database connections

Each API instance holds a pool of database connections. 3 instances × 10 connections = 30; a small managed database may allow only 25. Set pool sizes and max_instances together, or scaling up during a traffic spike will cause an outage.

Check yourself

Write a Locust (or k6) script with two user types: a counsellor (log in, list leads, open one, add a note) and a public visitor (ask the assistant). Run it against a local deployment, find the request rate where p95 exceeds 500 ms, and note what limits you first: CPU, database or something else.
