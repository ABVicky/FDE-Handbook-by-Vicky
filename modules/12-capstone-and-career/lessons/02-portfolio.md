# Lesson 02 — Building an FDE portfolio

**Time:** ~4 hours · **Core**

## What hiring managers look for

FDE hiring managers ask: *Can this person take a vague problem to a working system, with good judgement, and explain it to a client?* Your portfolio should answer that in five minutes.

## Shape: one flagship, two supporting

| Piece | Purpose | Candidates |
| --- | --- | --- |
| **Flagship** | Shows the whole lifecycle | Your capstone |
| **Supporting 1** | Depth in your specialization | AdmitFlow's assistant + evaluation, or a data pipeline |
| **Supporting 2** | Range or a real user | Your Field Track project, an open-source contribution |

## Each project's README (the write-up)

1. **One-sentence summary** and a screenshot or 60-second video
2. **The problem**, in the client's terms, with the baseline
3. **What you built** (architecture diagram) and **what you deliberately didn't**
4. **Results**: evaluation numbers, user outcomes, honestly
5. **Key decisions**: two or three ADR-style trade-offs
6. **What went wrong** and what you changed
7. **How to run it** in one command; how to run the tests

Sections 5 and 6 are where judgement shows. Most portfolios skip them.

## Repository hygiene

- Clean history with meaningful commits; CI badge green
- No secrets, no real personal data, no `node_modules`
- Issues or a short roadmap showing what's next
- Pinned on your GitHub profile, with a profile README linking the three projects

## Show the non-code work

FDE work is half communication. Include (anonymized) a discovery summary, a one-page proposal, an incident report, or your recorded client presentation. Very few candidates show these; it sets you apart.

## Check yourself

Write the README for your flagship using the seven sections, then ask someone who isn't technical to read the first three sections and tell you what problem it solves. Then ask an engineer to run it from a clean clone.
